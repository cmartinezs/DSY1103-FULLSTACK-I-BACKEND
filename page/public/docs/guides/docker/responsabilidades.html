Responsabilidades en Docker

Propósito: esta página separa qué debe resolver cada pieza cuando dockerizas los proyectos del curso. No reemplaza la guía paso a paso; sirve como mapa de responsabilidades para revisar una entrega.

Dockerfile

  • Define cómo se construye una imagen reproducible para cada microservicio.
  • Compila el proyecto en una etapa de build y copia solo el artefacto final a la imagen de runtime.
  • Declara WORKDIR, COPY, RUN, EXPOSE y ENTRYPOINT sin mezclar configuración de despliegue.
  • Ordena capas pensando en cache: dependencias primero, código fuente después.
  • No contiene credenciales, URLs reales de producción ni variables específicas de una máquina.

Imagen

  • Empaqueta la aplicación, runtime y dependencias con una versión identificable.
  • Debe poder ejecutarse igual en la máquina del equipo, CI o plataforma de despliegue.
  • Debe ser lo más liviana posible para el contexto: JRE slim, Alpine o Distroless cuando corresponda.
  • No guarda datos persistentes; los datos viven en volúmenes o servicios externos.
  • Se reconstruye cuando cambia el código, el pom.xml o la imagen base.

Contenedor

  • Es la instancia en ejecución de una imagen: un proceso aislado con red y filesystem propios.
  • Recibe configuración por environment, perfiles Spring y variables externas.
  • Expone logs por stdout/stderr para que docker logs y Compose puedan leerlos.
  • Debe poder reiniciarse sin perder datos críticos de base de datos.
  • No se edita manualmente por dentro; si algo falta, se corrige la imagen o Compose.

Docker Compose

  • Orquesta el sistema completo: microservicios, bases de datos, redes, volúmenes y variables.
  • Define nombres de servicio estables para comunicación interna: http://orders-service:8080.
  • Mapea solo los puertos que deben ser accesibles desde el host.
  • Centraliza configuración local con .env y valores seguros de ejemplo en .env.example.
  • Permite levantar y bajar todo con docker compose up y docker compose down.

Responsabilidades entre aplicación e infraestructura

Aplicación Spring Boot
  • Lee configuración desde variables de entorno o perfiles.
  • Expone endpoints y healthchecks consistentes.
  • Registra logs útiles con contexto de servicio, puerto y operación.
  • No hardcodea hosts como localhost para hablar con otros contenedores.
Infraestructura Docker
  • Entrega runtime, red, almacenamiento y arranque ordenado.
  • Configura variables, perfiles, puertos y dependencias entre servicios.
  • Persiste datos con volúmenes y evita que el estado dependa del contenedor.
  • Permite reproducir el entorno sin pasos manuales extra.

Errores de responsabilidad

  • Usar localhost entre contenedores en vez del nombre del servicio.
  • Poner contraseñas reales en Dockerfile, docker-compose.yml o el código Java.
  • Depender de comandos manuales dentro del contenedor después de levantarlo.
  • Construir una imagen distinta para cada instancia cuando solo cambia la configuración.
  • Guardar datos importantes dentro del filesystem efímero del contenedor.

Checklist de revisión

  • Cada microservicio tiene su Dockerfile multistage.
  • Compose levanta todo el sistema desde la raíz del proyecto.
  • Los servicios se comunican por nombres de Compose, no por IPs ni localhost.
  • Las bases de datos usan volúmenes nombrados.
  • Las credenciales reales quedan fuera del repositorio.
