MS Cliente — gato-client

Puertos :8081 / :8082 (instancias)

Rol y principios del cliente

El cliente es la fachada orientada al jugador. Administra su identidad localmente, recibe el serverUrl destino en las operaciones de juego, y delega al server correspondiente. Mantiene un registro local de qué partida pertenece a qué server.

  • Nunca retorna información de otros jugadores.
  • Cada operación de juego que crea una partida o se une a una recibe el serverUrl en el request.
  • Una vez registrada la asociación gameId → serverUrl, el jugador no necesita volver a indicar el server para esa partida.
  • Aplica fallback cuando el server no responde.
03.1

Modelos de dominio (local)

Player
  • id — Long, generado
  • username — String único
  • displayName — String
  • createdAt — LocalDateTime
GameRegistry

Registro local: mapea cada gameId al server donde fue creada.

  • id — Long, generado
  • gameId — Long (ID en el server)
  • serverUrl — String (ej: http://localhost:8080)
  • playerId — Long (jugador de este cliente)
  • registeredAt — LocalDateTime
03.2

Manejo de fallos — Fallback

Obligatorio: el cliente no puede fallar si el server no responde

Toda comunicación del cliente hacia el server debe tener un timeout configurado y un mecanismo de fallback. Si el server no responde o retorna un error 5xx, el cliente nunca debe propagar una excepción sin manejar: retorna una respuesta estructurada indicando el problema.

Timeout de conexión

El server no responde en el tiempo configurado (ej: 3 seg). El cliente retorna 503 Service Unavailable con un mensaje claro.

Error del server (5xx)

El server retorna un error interno. El cliente retorna 502 Bad Gateway informando que el server destino tuvo un problema.

Server no encontrado

El serverUrl ingresado no es alcanzable. El cliente retorna 503 antes de intentar registrar el gameId localmente.

Ejemplo de respuesta de fallback

{
  "error": "SERVER_UNAVAILABLE",
  "serverUrl": "http://localhost:8080",
  "message": "El servidor de juego no está disponible. Intenta más tarde.",
  "timestamp": "2025-06-01T10:30:00"
}

Se recomienda implementar el fallback usando un bloque try-catch sobre la llamada HTTP en la clase GatoServerClient, capturando ResourceAccessException (timeout/conexión rechazada) y HttpServerErrorException (5xx).

Acciones de juego — /api/game (proxy hacia el server indicado)
POST /api/game/create ▶ Crea una partida en el server indicado. El cliente inyecta el playerId y registra gameId→serverUrl localmente.
Headers + Body
X-Player-Id: 42

{
  "serverUrl": "http://localhost:8080",
  "gameType": "TIMED",
  "turnTimeoutSeconds": 30
}
Response 201 Created
{
  "gameId": 1,
  "serverUrl": "http://localhost:8080",
  "role": "X",
  "gameType": "TIMED",
  "turnTimeoutSeconds": 30,
  "status": "WAITING"
}
Nota: Si el serverUrl no responde, retorna 503 con la estructura de fallback. No se registra el gameId localmente si la creación falla.

POST /api/game/{gameId}/move ▶ Realiza una jugada. El cliente recupera el serverUrl del registro local por gameId — no se pide de nuevo.
Headers + Body
X-Player-Id: 42

1. Busca gameId en GameRegistry
2. Obtiene serverUrl del registro
3. Llama al server con playerId + pos
4. Fallback si el server no responde
