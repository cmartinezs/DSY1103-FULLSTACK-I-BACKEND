Capas tecnológicas requeridas

Nota: esta sección no explica Docker desde cero. Es un recordatorio explícito de qué tecnología pertenece a cada capa y qué se espera en los proyectos Fullstack I.

Capa de construcción

  • Dockerfile multistage por microservicio.
  • Stage builder con Maven y Java 21 para generar el JAR.
  • Stage runtime con JRE liviano para ejecutar el artefacto.
  • .dockerignore para excluir target/, .git/, archivos IDE y temporales.
  • Orden de capas pensado para cache: pom.xml antes que src/.

Capa de aplicación

  • Spring Boot 4.0 + Java 21 empaquetado como JAR ejecutable.
  • Perfil Docker separado: application-docker.yml o variables equivalentes.
  • Configuración externa con ${SERVER_PORT}, ${DB_URL}, ${DB_USER}, ${DB_PASS}.
  • Logs por consola; cero dependencia de archivos locales dentro del contenedor.
  • Endpoints de salud cuando el servicio participe en una arquitectura con dependencias.

Capa de orquestación local

  • Un docker-compose.yml en la raíz del sistema que levante todo.
  • Servicios nombrados según responsabilidad: api-gateway, ticket-service, db-ticket.
  • depends_on para orden básico de arranque y healthchecks cuando aplique.
  • Puertos host publicados solo para servicios que se consumen desde fuera de la red Docker.
  • Variables comunes en .env, con .env.example sin secretos reales.

Capa de red

  • Comunicación interna por nombre de servicio, no por IP ni localhost.
  • Red default de Compose suficiente para el entorno educativo, salvo que se pidan redes separadas.
  • Puertos internos se mantienen estables: Spring escucha en 8080 dentro del contenedor.
  • Puertos externos pueden variar: 8081:8080, 8082:8080, etc.
  • Gateway o frontend es la entrada pública cuando existe arquitectura de microservicios.

Capa de datos

  • Bases de datos como servicios Compose: H2 no necesita contenedor; MySQL/PostgreSQL sí.
  • Volúmenes nombrados para persistir datos: ticket-db-data, audit-db-data.
  • Una base o esquema por microservicio cuando hay persistencia independiente.
  • Credenciales inyectadas por variables, nunca hardcodeadas en Java.
  • Migraciones Flyway/Liquibase ejecutadas por la aplicación cuando el proyecto las use.

Capa de observabilidad

  • docker compose logs -f servicio debe mostrar el flujo útil de arranque y errores.
  • Los contenedores deben tener nombres legibles para depurar rápido.
  • Healthchecks documentados cuando se usan para esperar dependencias.
  • Errores de configuración deben fallar claro: variable ausente, URL incorrecta o puerto ocupado.
  • No depender de la UI de Docker Desktop para verificar que el sistema funciona.

Capa de seguridad

  • Sin secretos reales en repositorio.
  • Evitar :latest en imágenes base cuando la entrega requiere reproducibilidad.
  • Usuario no-root en imágenes orientadas a producción.
  • Publicar solo puertos necesarios en el host.
  • Separar configuración local de configuración productiva.

Capa de entrega

  • README con comandos exactos para construir, levantar, probar y apagar.
  • docker compose up --build debe ser suficiente para ejecutar el entorno local.
  • Documentar URLs finales con context path cuando aplique: /ticket-app.
  • Incluir ejemplos de request o colección Postman si el proyecto lo pide.
  • Antes de entregar: mvnw test y arranque Docker verificados.

Matriz de capas

Capa Archivo / tecnología Responsabilidad No debe resolver
Build Dockerfile, Maven, Java 21 Construir imagen reproducible. Configurar URLs específicas de ambiente.
Runtime JRE, JAR Spring Boot Ejecutar la aplicación dentro del contenedor. Persistir datos de negocio.
Orquestación docker-compose.yml Conectar servicios, variables, puertos y volúmenes. Compilar lógica de negocio.
Red Networks de Compose Resolver nombres de servicios y aislar comunicación interna. Exponer todo al host.
Datos PostgreSQL/MySQL, volúmenes Persistir estado fuera del ciclo de vida del contenedor. Guardar secretos en imágenes.
Operación Logs, healthchecks, README Permitir diagnóstico y ejecución reproducible. Reemplazar tests automatizados.
